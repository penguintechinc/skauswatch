# Service consolidation — 14 images → 5

**Status:** Draft design spec · **Target:** v2.1, after the v2.0.0 cutover (#92) · **Non-goal:** any change to product behavior, API contracts, or DB schemas.

Collapses the 13 skauswatch service images (excludes `endpoint-agent`, which is already leaving for `penguind` per `docs/v2-port/edr-module-spec.md` — out of scope here) into **5**: everything that is not a top-level product surface becomes a **module gated by its existing feature flag** inside a parent image, run-mode-selected per Deployment. Shared code that today is copy-pasted per service moves into shared crates — the same DRY move `v2.1-depgate.md` §3 already did for the scan engine, generalized to the rest of the workspace.

## 1. Goals & rationale

**Operational surface:** 14 images (13 services + webui) → 5. Fewer Helm charts, fewer SPIFFE identities to register/rotate, fewer `existingSecret`/ES256-keypair configs to manage per environment, fewer things that can independently drift out of sync (dependency versions, base-image digests, CI cache scopes).

**CI build time — the concrete win.** `.github/workflows/build.yml`'s `build-platform` job matrixes **14 services × 2 platforms (`linux/amd64`, `linux/arm64`) = 28 build jobs**, each a full `cargo build --release --locked` of the whole workspace (every service path-depends on `crates/skauswatch-*`, so there is no manifests-only fast path — see the Dockerfile comments in `services/depgate/Dockerfile` and `services/endpoint-agent/Dockerfile`). `linux/arm64` runs under QEMU emulation on `ubuntu-latest` GHA runners (no native arm64 runner in this workflow), and the two heaviest images — `scanner` (chromium + its full apt dependency tree) and `worker-codescan` (semgrep via pip + gitleaks/trivy/syft binary fetch+verify) — are exactly the ones already documented as 1–2h **each** on arm64/QEMU. Consolidating to **5 services × 2 platforms = 10 build jobs** cuts the matrix by 64% (28→10) and, more importantly, cuts the number of *from-scratch arm64/QEMU cargo builds* from 14 to 5 — the four services folding into `svc-scanner` and the four folding into `svc-vault` currently each pay their own full arm64 build; after consolidation that toolchain-heavy compile happens once per merged image instead of once per constituent service. `merge-manifests` (currently 14 manifest-list jobs) drops to 5 for the same reason.

**Code duplication:** see §4 — seven near-identical `rate_limit.rs`/`ratelimit.rs` files (125–238 lines each), 7 hand-rolled `error.rs` ApiError types (136–279 lines each), 4+ duplicated `health.rs` files, and cookie/CSRF auth logic that exists in exactly one service (`manager`) but conceptually belongs to the whole browser-facing surface.

**Non-goal:** this is not a rewrite. Every module's routes, DB schema, request/response shapes, and feature flags are unchanged. The parity bar is the same golden-parity harness already gating the v1→v2 port (`docs/v2-port/manager-contract.md`, `phase11-r3-r4-cutover-checklist.md`) — consolidation must reproduce byte-identical behavior, not improve it.

## 2. Module + feature-flag model

**Run mode** selects *which module set a Deployment activates* — it's a deployment-shape decision, read once at process startup (env var or `--mode` CLI arg), not re-evaluated per request. **Feature flag** gates *an individual capability* within an active module — evaluated per-request/per-tenant via PostHog (`feature_enabled`) + license entitlement (`has_feature`), can flip at runtime without a redeploy. These are orthogonal axes: a run mode decides the binary boots module X's router at all; a flag decides whether a specific route inside module X's router 403s for a given tenant today.

Every module reuses its **existing** flag from `services/manager/src/flags.rs` — no new flags are introduced by this consolidation:

```rust
MODULE_FLAGS: skauswatch.vault, skauswatch.codescan, skauswatch.depgate
CORE_FLAGS:   skauswatch.s3-scan, skauswatch.siem, skauswatch.asm, skauswatch.monitor,
              skauswatch.log-ingest, skauswatch.pki, ...
```

**"Won't we lose per-service scaling?" — no.** A single image deployed as several Helm `Deployment`s, each set to a different run mode via an env var / values override, preserves independent replica counts, HPA targets, and resource requests exactly as today — nothing here couples scaling to the image boundary. Concretely: `svc-scanner` deployed as `svc-scanner-object` (`--mode object`, N replicas sized for s3 bucket throughput), `svc-scanner-asm` (`--mode asm`, fewer replicas, more CPU for chromium), and `svc-scanner-code` (`--mode code`, replicas sized for the `codescan:tasks` queue depth) are three Deployments, three HPAs, three resource profiles — one image. The only thing consolidation removes is *separate container images*, not separate running processes or separate scaling knobs.

None of the 12 folding services have a `--mode` flag today — every `main.rs` reviewed (`manager`, `monitor`, `logs`, `codescan-backend`, `scanner`, `s3scan`, `worker-codescan`, `vault`, `worker-vault-sync`, `pki`, `sshca`) exposes only `serve` (default) / `healthcheck` / `openapi` subcommands via `clap::Subcommand`. Run-mode selection is new plumbing this consolidation adds, one binary at a time (§5).

**hub-api gRPC note:** `manager` and `pki` each run their own tonic gRPC server today (`services/manager/src/grpc`, `services/pki/src/grpc`, distinct SPIFFE roles per `service-auth-model.md` §1 — manager serves `ManagerService`+`S3ScanService` and is pki's sole `PkiService` caller). Since pki moves to `svc-vault`, not `hub-api`, this doesn't collapse two gRPC servers into one process — manager's `ManagerService`/`S3ScanService` gRPC surface stays in `hub-api` unchanged; it now calls `svc-vault`'s `PkiService` instead of a standalone `pki` pod, same mTLS contract, different pod behind it.

**svc-vault gRPC note:** `pki`'s `PkiService` gRPC server moves in as-is; `sshca` and `vault` have no gRPC role today (REST only, per `service-auth-model.md` §1) and stay REST-only inside the merged binary.

## 4. Shared-library strategy (the DRY win)

**13 existing `crates/skauswatch-*`** (workspace `Cargo.toml`): `auth`, `common`, `db`, `identity`, `scan-core`, `streams`, `telemetry`, `s3`, `vault`, `ai`, `proto`, `spire-entry`, `testkit`. These stay as-is — every one is already a cross-service dependency (see the per-service dependency table implied in §3).

**What's duplicated today that these 13 crates do NOT cover** (grepped across the 12 folding services):

| Duplication | Evidence | Extract to |
|---|---|---|
| Rate-limit middleware (`tower_governor` wiring) | 7 near-identical files: `manager/src/rate_limit.rs` (238 ln), `depgate/src/rate_limit.rs` (186), `logs/src/rate_limit.rs` (174), `vault/src/rate_limit.rs` (172), `monitor/src/rate_limit.rs` (172), `pki/src/ratelimit.rs` (135), `sshca/src/ratelimit.rs` (125) | New `skauswatch-web` (or fold into `skauswatch-common`) — one `governor_layer(cfg) -> GovernorLayer` |
| HTTP error taxonomy → `IntoResponse` mapping | 7 hand-rolled `ApiError` enums: `manager/src/error.rs` (279 ln) down to `monitor/src/error.rs` (136) — `skauswatch-common::error::Error` today is a bare 23-line taxonomy with no Axum `IntoResponse` impl at all | Extend `skauswatch-common` (or the same new `skauswatch-web`) with a standard `ApiError` + `IntoResponse` + the `{"status","data","meta"}` envelope shape from `backend.md` |
| Axum bootstrap (Router + middleware stack: trace, CORS, governor, auth extractor, health/readyz) | Every `main.rs` hand-assembles this (`manager`, `monitor`, `vault`, `codescan-backend` all call `Router::new()`/`axum::serve` directly with their own layer order) | `skauswatch-web::bootstrap(cfg) -> Router` — the biggest single win for `hub-api`, which will host 4 modules' worth of this scaffolding in one binary |
| HttpOnly cookie + `sw_csrf` double-submit auth (H2 audit fix) | Lives **only** in `manager/src/auth/cookies.rs` (373 ln) today — but `hub-api` is about to be the *entire* browser-facing surface (manager+monitor+logs+codescan-backend), so this needs to be gateway-level, not manager-module-level | Promote into `skauswatch-auth` (or `skauswatch-web`) as `hub-api`'s single cookie/CSRF layer, applied once at the gateway, not per-module |
| Health/readiness endpoints | 4+ duplicated `health.rs`: `manager` (245 ln), `codescan-backend` (174), `vault` (145), `pki` (167), plus `monitor/src/routes/health.rs` (184) | `skauswatch-telemetry` already owns "health/readiness endpoints" per its own crate description — these should have been calling into it; finish that consolidation here |
| Connector/scanner-tool registry pattern | `worker-codescan::scanner_tool::ScannerTool` trait (semgrep/gitleaks/trivy/syft as trait impls, `scanner_tool.rs`) is the exact shape DepGate's per-ecosystem clients (`npm.rs`, `crates_io.rs`, `oci_path.rs` — each "talks to exactly one configured upstream registry") and SIEM's not-yet-built connector layer need | Generalize `ScannerTool`-shape into a small `skauswatch-connector` trait crate (`async_trait`, `fn name()`, `fn run(input) -> Finding/Result`) that Sentinel's scanner tools, DepGate's ecosystem clients, and SIEM's future ingest connectors all implement |
| OCSF normalization | `services/logs/src/ocsf.rs` (465 ln, byte-for-byte port of v1 `ocsf/normalizer.py`) — `edr-module-spec.md`'s OCSF-bridge design (§3/§7) is explicitly derived from this file plus manager's `endpoint.rs`, and will need the same normalizer | Extract to `skauswatch-ocsf` — consumed by `hub-api`'s `logs` module today, and by `penguind`'s OCSF bridge tomorrow (cross-repo consumer, see below) |
| Config loading | `skauswatch-common::config::load_config` already exists and is generic (figment, prefixed env vars) — confirm all 12 services actually use it rather than hand-rolling `std::env::var` (several `main.rs` files read `API_PORT` via ad hoc `std::env::var(...).ok().and_then(...)` instead) | No new crate — audit-and-migrate onto the existing `load_config` during each migration step in §5 |

**penguin-libs (Rust): "none published yet."** This consolidation is the forcing function to start one. `skauswatch-scan-core` (ClamAV+YARA-X, already shared by s3scan/scanner/DepGate/Sentinel per `v2.1-depgate.md` §3) and the new `skauswatch-ocsf` are the two strongest candidates to land in `penguin-libs` rather than staying `skauswatch`-local, because **`penguind` (EDR, `docs/v2-port/edr-module-spec.md`) is a confirmed second consumer of both** — it needs the OCSF bridge (§3/§7 of that spec) and will eventually want the same malware-scan primitives for on-host file scanning. Extracting `skauswatch-web` (bootstrap/middleware/error/rate-limit) into `penguin-libs` is a stretch goal for the same reason: any future Rust service at PenguinTech needs the identical Axum+governor+auth-cookie scaffolding, and `general.md`'s "contribute to `penguin-libs` before writing custom auth/DAL/logging equivalents" rule applies directly once a second Rust product exists to justify it.

## 5. Migration plan / order

Safest-first — each step ships behind the module's existing flag (already OFF-by-default-capable), is verified against the golden-parity harness before merge, and shrinks the CI matrix incrementally rather than in one cutover.

| Phase | Change | Why safest at this position |
|---|---|---|
| **P1** | Fold `worker-vault-sync` into `svc-vault`; fold `worker-codescan`'s code-scan path into `svc-scanner`. | Trivially "one product split by convention" — each pair is already an api/worker split of the same domain (vault secrets + its cloud-sync worker; code scanning + its own worker), sharing DB schema and stream topics already. Lowest risk: no cross-module routing changes, no gateway work. |
| **P2** | Merge `pki` + `sshca` into `svc-vault`; introduce `svc-vault`'s `--mode secrets \| pki \| sshca \| sync`. | Both CAs are already "vault-adjacent" secrets material; this is the first real run-mode introduction (§2) but still single-domain (crown jewels stay together, isolation posture doesn't get worse — see §7). |
| **P3** | `hub-api` = fold `monitor` (SIEM) + `logs` (log-ingest) + `codescan-backend` routes behind `manager`'s existing Axum router as a gateway; extract `skauswatch-web` bootstrap (§4) in the same pass since 4 modules' worth of duplicated scaffolding is now colocated and impossible to ignore. | Highest module count (4→1) but no native-dependency risk (all four are `ca-certificates`-only Debian images today) — the risk here is entirely in routing/auth correctness, which the golden-parity harness is built to catch. |
| **P4** | `svc-scanner` = fold `s3scan` (object) into the already-P1-merged scanner+worker-codescan image; last because it's the chromium whale (§3) — merging it earlier would have meant carrying the heaviest build through every intermediate phase's CI runs. | Runs last so the biggest single image only exists for the shortest possible window before the matrix shrink lands. |

Each phase: keep the hub-API/ingest **contracts stable** (no OpenAPI breaking changes — `services/*/openapi/v1.yaml` content moves, doesn't change shape); run the golden parity harness (the same one gating v1→v2, per `manager-contract.md` and `phase11-r3-r4-cutover-checklist.md` §5) against the merged image before it replaces the standalone ones in any environment; migrate the corresponding Helm chart(s) in the same PR as the code merge, never after; shrink `build.yml`'s matrix (§6) only once a phase's constituent services are fully retired from `main`, not speculatively.

## 6. Chart / CI / deploy impact

**Helm:** 14 charts (`k8s/helm/{manager,monitor,logs,codescan-backend,scanner,s3scan,worker-codescan,vault,worker-vault-sync,pki,sshca,depgate,webui,endpoint-agent}`, endpoint-agent leaving separately) → 5. Each existing chart's `alpha.yml`/`beta.yml`/`gamma.yml`/`production.yml` values-file-per-environment pattern carries forward; run modes become **values-selected Deployments** within one chart (e.g. `svc-scanner`'s chart renders three `Deployment` resources — object/asm/code — off one set of templates, mode passed as an env var per the values file), the same shape `depgate`'s and every current chart's `deployment.yaml`+`_helpers.tpl`+per-env values files already use.

**CI:** `build.yml`'s `build-platform` and `merge-manifests` matrices both drop from the current 14-entry `service:` list to 5 entries — see §1 for the concrete build-time math. `rust.yml` (fmt/clippy/test/coverage) is a workspace-wide gate already and is unaffected by image count.

**Existing patterns that carry into the merged charts unchanged:**
- `existingSecret` + ES256-keypair pattern (`vault/values.yaml`'s `existingSecret: ""` + `_helpers.tpl`'s `default (printf "%s-secret" ...)` fallback) — each merged image keeps one secret per environment, same shape.
- `tower_governor` rate limiting — becomes the shared `skauswatch-web` layer (§4) but the per-route limits configured today stay per-route inside the merged router.
- `CiliumNetworkPolicy` default-deny + same-namespace-allow (every chart's `templates/ciliumnetworkpolicy.yaml` follows the identical "selecting this pod denies everything else" pattern, e.g. `depgate`'s and `manager`'s) — 5 policies instead of 12, each scoped to its merged pod's actual callers.
- SPIRE chart's `autoEnroll.services` list (`k8s/helm/spire/values.yaml`) shrinks from ~12 per-service entries to 5 — each merged image gets **one** SPIFFE identity instead of N (see §7 for what this costs).

## 7. Tradeoffs / risks / non-goals

**Larger blast radius per image.** A bug or CVE in one module's dependency tree now requires redeploying (and re-auditing) the whole merged image, not just the affected service. `svc-scanner` is the sharpest edge of this: a chromium CVE now forces a rebuild/redeploy of the object-scan and code-scan run modes too, even though neither touches chromium.

**`svc-scanner` size.** Chromium's apt closure (GTK/NSS/X11/fonts — already "expected and required, not a bloat regression" per the scanner Dockerfile's own comment) plus semgrep's PyPI install plus three pinned Go binaries (gitleaks/trivy/syft) all land in one image. This is the single largest image in the fleet post-consolidation by a wide margin; `--mode object` and `--mode code` Deployments carry chromium's weight even though they never invoke it.

**`svc-vault` isolation — a real tension with the standing namespace convention.** `penguintech.md`'s Cluster Contexts rule states "Namespace in every context is the product name only" — i.e., today every skauswatch service, `vault` included, shares one `skauswatch` namespace. Giving `svc-vault` its **own** namespace (as its crown-jewels sensitivity arguably warrants — both CAs + all secrets crypto in one process, per §3) would be a deviation from that convention, not an application of it. Two honest options, not a decision made here: (a) accept the deviation explicitly, with user sign-off, as a security-driven exception the way `devops-containers.md`'s root-exception process works; or (b) keep `svc-vault` in the shared `skauswatch` namespace and achieve isolation purely via a tighter `CiliumNetworkPolicy` (deny-by-default, explicit allowlist of only `hub-api` as a caller) + dedicated RBAC/ServiceAccount + its own SPIFFE identity — no colocation *requirement* on internet-facing modules is actually enforced by namespace boundaries in this cluster model anyway, since Cilium policy is what does the enforcing. Flagged as an open decision (§8).

**SPIFFE identity collapse.** `service-auth-model.md` §1 registers a distinct `spiffe://penguintech.io/<env>/<service>` per service today, several with distinct gRPC peer-allowlists (e.g. pki's `PkiService` today allows `allow_exact(spiffe://.../manager)` only). Consolidation collapses 4 identities into `hub-api`'s one, 3 into `svc-scanner`'s one, and 4 into `svc-vault`'s one — mTLS-based inter-module authorization at the current per-service granularity is lost; anything that needs it becomes an in-process call instead. Acceptable because none of the collapsing services call each other over gRPC/mTLS *except* manager→pki (manager stays in `hub-api`, pki moves to `svc-vault`, so that one call becomes a real cross-image gRPC call and is the one identity pair that must be preserved, not collapsed).

**SIEM-in-hub-api footprint.** `monitor` (SIEM) is the least-REST-only-flavored of the four `hub-api` modules — it has its own ingest pipeline (`ingest.rs`), threat-intel enrichment (`threat_intel.rs`), and OCSF-adjacent event models (`models.rs`, 664 lines) that are closer in shape to a stream-processing worker than a thin REST router. If SIEM's throughput/latency profile ends up incompatible with sharing a process (and its own Deployment/HPA) with manager/logs/codescan-backend's REST traffic, it should be pulled back out as its own image rather than forced to fit — see Open Decisions.

**Behavior preserved, not improved.** Every route, DB table, and flag name is unchanged by this consolidation; this is a container/process boundary refactor, not a feature or API change. The cross-module **exec-report aggregator** — wanted independently by `v2.1-codescan-sentinel.md` (exec+security reports), `v2.1-depgate.md` (compliance reports), and `edr-module-spec.md`/SIEM (posture reporting) — naturally lands as a `hub-api` module once monitor+codescan-backend share a process: it can read all three modules' findings tables directly rather than fanning out over the network, which is one of the few net-new capabilities this consolidation makes *cheaper*, even though building it is out of scope here.

## 8. Open Decisions

1. **`svc-vault` namespace isolation** (§7): full namespace deviation (needs explicit user approval, sets a precedent) vs. NetworkPolicy-only isolation within the shared `skauswatch` namespace. Recommend deciding this at P2 kickoff (§5), not speculatively here.
2. **DepGate's scan path:** does `depgate` call `svc-scanner` internally for its malware-scan step, or keep its own direct `skauswatch-scan-core` invocation (as it does today, per its Cargo.toml deps)? `v2.1-depgate.md` §3 already designed scan-core as a shared crate specifically so DepGate does *not* need a network hop to `svc-scanner` for this — recommend keeping DepGate's current in-process `skauswatch-scan-core` call and treating this consolidation as reinforcing that choice, not revisiting it. Listed as open only because the 5-image map puts scanning capability in two places (`svc-scanner` and `svc-depgate`) and a future reader may reasonably ask why they don't share a process.
3. **Is SIEM a `hub-api` module or a 6th image?** (§7). Recommend proceeding with the `hub-api` plan in P3 but instrumenting monitor's ingest throughput before and after the merge; if `hub-api`'s p99 latency or monitor's ingest lag regresses measurably, split SIEM back out rather than forcing the 5-image target.
4. **`skauswatch-web` crate boundary:** one new crate covering bootstrap+error+rate-limit+cookie-auth, or split into 2–3 smaller crates (e.g. `skauswatch-web` for bootstrap/error/rate-limit, keep cookie/CSRF inside `skauswatch-auth` since it's fundamentally an auth concern)? Recommend deciding during P3 spike work when the actual code is in hand, not in this document.
5. **`skauswatch-scan-core`/`skauswatch-ocsf` → `penguin-libs` timing:** land them in `penguin-libs` now (blocks on `penguind`'s repo/build being ready to consume a git-rev-pinned Rust dependency, same pattern as `penguin-licensing`'s `rev = "..."` pin today) or keep them `skauswatch`-local until `penguind` actually needs them and migrate then? Recommend the latter — extract to `skauswatch-ocsf`/harden `skauswatch-scan-core` now, defer the `penguin-libs` move to whenever `penguind` work starts per `migrating-to-penguin-libs` skill's normal trigger.

## 9. Timing

Recommend **v2.1, after the v2.0.0 cutover (#92)**. This consolidation is a large structural refactor (moving routes/DB pools/gRPC servers between binaries) — starting it before v2.0.0 ships would reshape the exact set of files the golden-parity harness is currently gating, delaying the cutover to chase a moving target. Doing it post-cut, with the parity harness already proven against v1 and now reusable as the safety net for merge-vs-merge comparisons, is the safer sequencing. **If the user instead wants to hold v2.0.0** to ship a smaller image count at launch, that is a real alternative worth surfacing explicitly — but it trades a known, near-term release date for an unscoped amount of additional pre-release risk on a refactor this document deliberately has not yet had golden-parity-tested in code. Default recommendation stands: ship v2.0.0 first, consolidate in v2.1.
