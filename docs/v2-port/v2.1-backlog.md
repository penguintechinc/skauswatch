# v2.1 Backlog

Items deliberately deferred out of v2.0 to protect the big-bang scope
(zero-schema-change invariant, "no new features in v2.0"). Each entry
records why it is safe to defer.

## Research router: live external lookups

`/api/v1/research/*` in v1 was entirely runtime-broken — every handler
raised `AttributeError` on the missing `config.research` attribute and
returned 500, and the client wiring (`_get_research_clients`) called
methods that do not exist. There is no working v1 behavior to preserve.

v2.0 ships the contract-decided deterministic surface (auth, validation,
shodan/maltego enable gates, exact `GET /config` payload, intended
empty-result envelopes). Implementing *working* WHOIS/DNS/ASN/Shodan/
Maltego lookups requires new network clients (DNS resolver, WHOIS, HTTP
integrations) — that is new functionality, not a port, so it lands in
v2.1 behind `skauswatch.research`.

Safe to defer: v2.0 is strictly better than v1 here (deterministic
envelopes instead of 500s); nothing customers currently rely on is lost.

## MySQL/MariaDB support (from the approved plan)

`DB_TYPE=mysql` deferred — no production MySQL head exists; sqlx AnyPool
sacrifices compile-time type safety. `skauswatch-db` trait surface keeps
it additive.

## Drop inert `alembic_version` tables

Left in place by the v2.0 sqlx-migrate baseline stamping; drop in v2.1.

## CodeScan Sentinel — AI-assisted dependency & vulnerability management

Net-new: scheduled scan of configured repos' default + latest release branches →
outdated deps + CVEs + SAST + license + secrets via OSS tools (semgrep/gosec/trivy/
osv-scanner/…) → AI-assisted reachability + severity triage (models + ShieldGemma
guardrails **consumed from WaddleAI**, not rebuilt here) → policy-engine-governed
actions (document / alert / grouped fix-PR) → exec + security reports. Opt-out per
repo. Full design + phasing (P1 report-only Dependabot replacement → P4 grouped
auto-fix PRs) in [`v2.1-codescan-sentinel.md`](v2.1-codescan-sentinel.md).
Deterministic tool scans stand alone (Professional); AI-assisted intelligence gates
Enterprise via WaddleAI. Flag `skauswatch.codescan.sentinel`.

## scanner ASM subsystem (LARGE)

v1 `scanner` had a full attack-surface-management subsystem:
`masscan`, `nuclei`, `openvas`, `zap`, `screenshot`, `cert_inspector`,
`banner_grabber` + their parsers (~15k LOC). The Rust port covers the
malware-scan path (YARA via yara-x 1.19.0 — EICAR-proven — + ClamAV
INSTREAM) fully.

**BUILT in v2.0 (Phase 12 / P12-A):** the ASM pipeline is functional —
masscan enumeration, `banner_grabber`, TLS `cert_inspector`, diff-vs-prior,
and headless-chromium `screenshot` capture — all tenant-scoped and DB-backed
(`asm_*` tables, migration 0006), driven by the manager `asm` router
publishing `scanner:tasks` (the old proxy-to-a-nonexistent-HTTP-server is
gone).

**Still unbuilt:** `nuclei`/`zap`/`openvas` standalone scan types — v1 had
them but with NO trigger/client path (unreachable), so they are not a cutover
blocker; disposition TBD (not auto-deferred to v2.1 at this time).

## sshca

- RSA CA-key support ⏳ **OPEN**: blocked on `ssh-key` 0.7 going stable (0.7.x
  is RC-only; house rules forbid pre-release). v2 is Ed25519/ECDSA-only with
  a fail-loud RSA rejection at startup. (v1's SSH CA emitted invalid
  certs for all key types, so nothing regressed.) Unblocks when `ssh-key` 0.7
  ships stable.
- Durable ssh-cert storage ✅ **BUILT** (P12-E): issued certs persist in pki's
  `ssh_certificates` table (`pki/migrations/0001_pki_schema.sql`,
  `sshca/src/store.rs`) — revocation survives restart.
- ssh-keygen interop test ✅ **BUILT**: `pki/src/ca/ssh.rs` shells real
  `ssh-keygen` in-test to verify emitted certs against OpenSSH.

## Vault sync — real secret payload plumbing ✅ BUILT

v1 (and the initial 1:1 v2 port) published only `{integration_id, event_type,
timestamp}` to the sync stream, so `SyncHandler::do_push` — which needs
`secret_id`/`secret_name`/`encrypted_value`/`encrypted_dek`/`dek_version` —
always failed to decrypt and skipped, for every provider including AWS.
**BUILT (P12-B):** `trigger_sync` now enumerates the tenant's in-scope secrets
and publishes one real ciphertext-carrying `push` message per secret
(`vault/src/routes/sync.rs::push_fields`); `do_push` decrypts the forwarded
ciphertext with the same envelope MEK and calls the provider
(`worker-vault-sync/src/handler.rs:170`). Covered end-to-end by
`trigger_sync_publishes_a_real_decryptable_secret_payload_to_the_stream` plus
the handler's own `do_push` tests. Envelope encryption is preserved end-to-end
(vault forwards ciphertext byte-for-byte; only the worker ever decrypts).
